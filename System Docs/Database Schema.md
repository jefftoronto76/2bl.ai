# Database Schema

## Database Schema

All tables are multi-tenant. Every data access must respect `tenant_id`.
Row Level Security is enabled on all 32 tables, but only 3 have real
policies (confirmed via live query 2026-08-04) and the service-role client
used for nearly all server-side data access bypasses RLS by default —
actual tenant isolation is enforced in application code via `tenant_id`
scoping (`getAuthContext()`), not by the database. See CLAUDE.md's "Highest
Data Security" principle and `System Docs/Known Gaps.md` for the current RLS
posture. RLS policies are Studio-managed and not tracked in git;
re-verify this figure periodically rather than assuming it's permanent.

### Block Types

| Type | Purpose |
|------|---------|
| `identity` | Identity & Voice — who Sage is, tone, personality |
| `knowledge` | Factual context about the business, owner, services |
| `guardrail` | Rules and constraints on Sage's behavior |
| `process` | Step-by-step instructions for how Sage should handle situations |
| `output_format` | How Sage should structure and present its responses |

**Compile order**: Types are compiled into the master prompt in this
fixed order: identity (1st), knowledge (2nd), guardrail (3rd), process
(4th), output_format (5th) — per `TYPE_COMPILE_ORDER` in
`services/prompt/block-types.ts` and the matching `COMPILE_ORDER` array
in `services/prompt/compile.ts`. Within each type, blocks with `order > 0`
come first ascending by `order`; blocks with `order` = 0 or null come
last, ordered by title ascending. This order is enforced in
`/api/admin/prompt/compile` and sourced from `block-types.ts`'s
`TYPE_COMPILE_ORDER`/`TYPE_LABELS` — do not change without updating both.
`TYPE_LABELS` itself is consumed by `components/admin/content/*`
(`BlockEditForm`, `BlocksFilters`, `BlocksToolbar`, `SegmentedTokenMeter`)
and `app/admin/prompt-studio/blocks/TokenDonut.tsx`, not by
`BlocksTable.tsx` — that file only imports the `BlockType` type.
