# Audit Service

### Audit service (`services/audit/`)

Centralised audit and auth-event logging. Server-only. Imported as
`@/services/audit` (barrel) or `@/services/audit/types` (types only).

**Timestamp convention: all `audit_events` / `auth_events` timestamps are
stored in UTC** (`created_at timestamptz default now()` — Postgres stores the
UTC instant). Queries, reports, and any time-window filtering must convert
to/from local time explicitly; never assume rows are in the server's or
viewer's local timezone.

| `types.ts` | `AuditAction` (const + type), `AuthEventType` (const + type), `AuditEventInput`, `AuthEventInput` | Typed action-name constants (`AuditAction.BLOCK_UPDATE = 'block.update'`, etc.) and input interfaces matching the DB schema. Eliminates magic strings at every call site. `AuthEventType` covers: `sign_up`, `sign_in`, `sign_in_failed`, `otp_sent`, `otp_verified`, `session_created`, `session_revoked`, `user_deleted`, `admin_access`, `admin_access_failed`. Member-lifecycle `AuditAction` constants added 2026-06-12: `MEMBER_INVITE_CREATED = 'member.invite_created'`, `MEMBER_INVITE_ACCEPTED = 'member.invite_accepted'`, `MEMBER_ROLE_UPDATED = 'member.role_updated'`, `MEMBER_STATUS_UPDATED = 'member.status_updated'`, `MEMBER_HARD_DELETED = 'user.hard_deleted'` (note: the enum key is member-scoped but the stored string value is `user.hard_deleted` — a naming holdover from when this action targeted the `users` table directly). `MEMBER_INVITE_RESENT = 'member.invite_resent'` and `MEMBER_INVITE_REVOKED = 'member.invite_revoked'` back the resend/revoke routes. `MEMBER_INVITE_OPENED = 'member.invite_opened'` (added 2026-07-11, invite-link tracking) is fired fire-and-forget with `actor_type: 'anonymous'` from the public `GET /invite/[token]` redirect route — the only `AuditAction` write with no authenticated actor. `CHAT_MEDIA_CONTEXT_RESOLVED = 'chat.media_context_resolved'` (added 2026-08-04) diagnoses whether `resolveMediaContext` (`services/chat/server/media-context.ts`) produced usable output for a chat turn — added after Heirloom guide reports of not seeing uploaded photos/files even when the DB showed `status = 'ready'`, a case the prior DB-error-only log didn't cover. Written from two sites per turn, deliberately, for visibility at both the caller and the resolver: `services/chat/server/index.ts`'s `streamChat()` logs unconditionally after its `Promise.all` resolves, with metadata `{ clientSentItems, contextLength, hasAttached, hasFailed, hasInProgress }` (booleans derived from whether the built context string contains each section header); `media-context.ts`'s `resolveMediaContext()` logs from inside itself, but only on the path that reaches its DB query (skipped by the function's early-return for no media items/tenant/member), with metadata `{ clientSentItems, readyCount, failedCount, inProgressCount, contextLength }`. Neither site ever includes `derived_content` or other extracted file content — counts and presence flags only. Media-pipeline actions added 2026-08-05 as part of the broader sweep (`System Docs/Known Gaps.md`, PRs #280/#281): `MEDIA_UPLOAD_DEDUPED = 'media.upload_deduped'` fires from `app/api/media/upload-url/route.ts` when a client-supplied `content_hash` matches an existing row for the same member+chat — metadata carries the matched item's id/status, never file content. `MEDIA_UPLOAD_REJECTED = 'media.upload_rejected'` (added 2026-08-12) fires from the same route's `logUploadRejected` helper for every rejection that happens *before* a `media_items` row exists — until this addition these had zero audit trail under any action. One shared action, not one per rejection type (same reasoning as `MEDIA_PROCESS_FAILED`'s `pipeline_step`): `metadata.reason` distinguishes `invalid_json`, `missing_filename`, `missing_mime_type`, `missing_file_size`, `heic_unsupported`, `unsupported_mime_type`, `file_too_large`, `unclassifiable_mime_type` (present for defensiveness — currently unreachable, since every `ACCEPTED_MIME_TYPES` entry already classifies successfully), and `member_not_found`. `target_type: 'upload_attempt'`, `target_id: null` — there is no row yet to attach the event to. Logged via the base `logEvent` directly, not the `logMediaEvent` wrapper (which hardcodes `target_type: 'media_item'` and requires a `media_item_id`) — same precedent `resolveMediaContext` already set for `CHAT_MEDIA_CONTEXT_RESOLVED`. Deliberately excludes two earlier failure points in the same route: an unauthenticated request (401) and an unresolvable tenant (400) — auth/tenant-resolution failures are a different category from "this upload attempt was rejected," out of scope for this action. `MEDIA_RETRY_REQUESTED = 'media.retry_requested'` / `MEDIA_RETRY_FAILED = 'media.retry_failed'` fire in pairs (sharing one `correlation_id`) from `app/api/media/[id]/retry/route.ts`, the former on successful re-dispatch to `processMediaItem`, the latter only if that fire-and-forget call itself rejects. The remaining five — `MEDIA_FILE_UPLOAD_RECEIVED` / `MEDIA_FILE_UPLOAD_FAILED`, `MEDIA_PDF_EXTRACTION_RECEIVED` / `MEDIA_PDF_EXTRACTION_FAILED`, and `MEDIA_FILE_CLEANUP_FAILED` — are logged from `services/content/assets.ts`'s Anthropic Files API helpers (`uploadFileToAnthropic`, `extractTextFromPdf`, `deleteAnthropicFile`) via `logAiMediaEvent`, gated on an optional `MediaAuditContext` the caller supplies; the admin document-upload flow (`app/api/admin/assets/upload/route.ts`) has no `media_items` row and passes no context, so it gets no logging from these five actions, unchanged from its prior behavior. These pinpoint which specific internal step of PDF extraction succeeded or failed, distinct from the bracketing `AI_MEDIA_REQUEST_SENT` / `AI_MEDIA_RESPONSE_RECEIVED` / `AI_MEDIA_REQUEST_FAILED` actions `services/media/processor.ts` logs around the whole attempt. As with `CHAT_MEDIA_CONTEXT_RESOLVED` above, none of these ever log extracted text or file content — only ids, status, byte length, and error strings. `MEDIA_CHAT_ID_BACKFILLED = 'media.chat_id_backfilled'` / `MEDIA_CHAT_ID_BACKFILL_FAILED = 'media.chat_id_backfill_failed'` (added 2026-08-06, PR #291) fire from `app/api/sessions/route.ts`'s `POST` handler when the request carries `mediaItemIds` — an attachment uploaded before its session existed (the first message of a brand-new conversation always uploads before this route runs) has a `media_items` row with `chat_id: null`, which no client-side status mechanism (Realtime, catch-up, the poll — all `chat_id`-filtered) can ever find again; this pair closes that gap by backfilling `chat_id` in the same request that creates the session. Logged one event per `media_item_id`, not one aggregate event per request: `MEDIA_CHAT_ID_BACKFILLED` (`outcome: 'success'`) for every id the update actually matched; `MEDIA_CHAT_ID_BACKFILL_FAILED` (`outcome: 'failure'`) for every id that didn't (already set, wrong owner, or not found — `metadata.reason`), and again for every requested id if the update itself threw (`metadata.error`). All three code paths — the member-resolution failure, the backfill update throwing, and even a `logMediaEvent` call itself throwing — are caught internally and can never fail the session-creation response; the point of these two actions existing is durable visibility into a path that used to be a silent fire-and-forget, not just successful-path logging. `MEMORY_CREATED = 'memory.created'` (Heirloom memory bookmark; broadened 2026-08-06, PR #288) fires from `services/crm/memories.ts`'s `createMemoryFromAnchor` on every attempt, `outcome: 'success'` or `'failure'`, `actor_type: memberId ? 'user' : 'anonymous'`. Previously only the terminal DB-insert-failure branch was logged (console-only elsewhere); every other failure branch now logs too, each with a distinct `metadata.error_detail`: `session_lookup_failed`, `anchor_not_found`, `anchor_content_not_string`, `empty_body_after_marker_strip` (all in `createMemoryFromAnchor`), plus whatever `createDraftMemory` itself returns as `error` on its own failure — either a DB error message, or (since PR #288) the fixed string `'An account is required to save memories.'` when the acting member is anonymous or not yet linked to a `users` row (`artifacts.user_id` is `NOT NULL`; see `Utilities/CRM.md`'s `memories.ts` row). `app/api/sessions/[id]/memories/route.ts`'s `POST` handler also logs `MEMORY_CREATED` failures for its own pre-service validation branches (also added 2026-08-06): `tenant_resolution_failed`, `invalid_request_body`, `missing_anchor_message_id`, `invalid_source_kind`. One failure mode is deliberately never logged here: a client-side `fetch()` throw (offline, DNS failure) never reaches the server at all, so it can't reach `audit_events` by definition — `services/chat/ui/v1/useMemories.ts`'s `'network'` `ChatErrorType` classification (see `Utilities/Chat UI.md`'s `useMemories.ts` row) is the only mitigation for that one case, an accepted limitation rather than a gap. **Story/member-orphan/session-context actions, not previously listed here:** `MEMBER_USER_RESOLVE_FAILED = 'member.user_resolve_failed'`, `MEMBER_LINK_UPDATE_FAILED = 'member.link_update_failed'`, `MEMBER_ORPHAN_CLEANUP_FAILED = 'member.orphan_cleanup_failed'`, `MEMBER_ORPHAN_RECONCILED = 'member.orphan_reconciled'` (documented in `Utilities/Members.md`'s own rows). `CONVERSATION_CREATE = 'conversation.create'` / `CONVERSATION_UPDATE = 'conversation.update'`. `MEMORY_KEPT = 'memory.kept'` / `MEMORY_DISCARDED = 'memory.discarded'` / `MEMORY_BLOCKS_REVISED = 'memory.blocks_revised'`. Story lifecycle (Real Story Creation, 2026-08-09 onward): `STORY_CREATED = 'story.created'`, `STORY_DISCARDED = 'story.discarded'`, `STORY_DESCRIPTION_UPDATED = 'story.description_updated'`. | `audit.ts` | `logEvent(input: AuditEventInput): Promise<void>`, `logAuthEvent(input: AuthEventInput): Promise<void>` | Thin service-role writes to `audit_events` and `auth_events` respectively. **Fire-and-forget** — all errors are caught and `console.error`'d; neither function ever throws, so a logging failure never blocks or fails the originating request. Call with `void logEvent(…)` from API routes. |
| `index.ts` | barrel | Re-exports `logEvent`, `logAuthEvent`, `AuditAction`, `AuthEventType`, and both input types. |

`logEvent` is called (with `void`) from every mutating admin API route,
every platform tenant route, every session route, and the Heirloom
membership-claim route. **Every `logEvent` / `logAuthEvent` call site passes
`tenant_id` (2026-06-11):** admin routes from `authCtx.tenant_id`, public/
anonymous surfaces (including `/api/auth/log`, the Clerk webhook, and the
`get-auth-context` admin_access_failed path) via host-based
`getTenantFromRequest` resolution; the platform tenant routes also stamp the
host-resolved id (null remains possible and still reads as platform-level). `logAuthEvent` is called from
`services/auth/get-auth-context.ts` (unauthorized-access path) and from
`app/api/auth/log/route.ts` (client-side step-by-step auth flow events via
`useAuthFlow`).

**Both DB tables have existed since 2026-06-08** (`audit_events`, `auth_events`
— see `System Docs/DB_CHANGELOG.md`'s `## 2026-06-08` entries for the exact
SQL) and have been receiving rows since then. The fire-and-forget/swallowed-
error behavior described above (`audit.ts`'s row) is a general resilience
property, not a workaround for missing tables — a genuine write failure
(bad payload, RLS, connectivity) still logs to `console.error` and swallows
rather than throwing, exactly as documented, but that's no longer the common
case.
