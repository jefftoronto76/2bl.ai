# Members Service

### Members service (`services/members/`)

Member invite and lifecycle operations for the `members` table. Server-only. The `invites` table is retired — invite state now lives on `members` directly via `token` / `used_at` / `invited_name` / `status = 'invited'`. Token generation uses `crypto.randomBytes(24).toString('base64url')` (32-char URL-safe string).

| File | Exports | Purpose |
|------|---------|---------|
| `members.ts` | `createMemberInvite`, `validateMemberToken`, `memberTokenExists`, `linkInvitedMember`, `acceptInvite`, `hardDeleteMember` (+ `MemberInviteRow`, `MembersResult`, `HEIRLOOM_TENANT_ID`) | `createMemberInvite(tenantId, actorId, invitedName?, email?, phone?, autoOpen?, primer?, storyId?)` — inserts a members row with status='invited', generates token, `expires_at` stamped `INVITE_TTL_DAYS` (14) out, writes email/phone when supplied (for contact-lock invites), stamps `invited_by = actorId` for provenance (null actor = column left unset — seeded/self-service, or a member-initiated invite where the inviting member's own `users.id` is passed as `actorId`, see `/api/heirloom/invites` in `System Docs/API Routes.md`), writes `primer` when non-empty (the `members.primer` value injected into MEMBER CONTEXT on every chat turn — `InviteMemberModal.tsx`'s admin flow and `InviteCollaboratorsModal.tsx`'s member-facing flow both write it through this same param), sets `auto_open` when `autoOpen === true`, fires `MEMBER_INVITE_CREATED` audit with a `metadata` object of `has_*` presence booleans for every arg plus `auto_open` (boolean) — **and, added 2026-08-10 (invites-collaboration-modal), `story_id`:** which story a collaborator invite is "for," from the sidebar's per-story invite trigger. **Not a real column or relationship** — there is no `stories` table yet (Stage 2, in flight; see `System Docs/Known Gaps.md`) and no story-collaborator join table, so `storyId` is recorded only in this one audit event's metadata as a provisional bridge, never persisted on the `members` row itself; read it back from `audit_events` if the story tie needs reconstructing before the real schema lands. Do not build against this as the final shape. `validateMemberToken(token)` — returns the members row when the token exists and `used_at IS NULL`. Its select list and the `MemberInviteRow` interface were missing `phone` until 2026-08-14 (PR #372) despite `createMemberInvite` already writing it — both now include it, alongside the pre-existing `email`/`name`/`invited_name`, so the invited row's phone is available to pre-fill `MagicLinkCard`'s sign-up form (`app/heirloom/page.tsx` → `chatStore.tsx` → `MessageList.tsx`, see `System Docs/Public Site.md`'s `chatStore` row). `memberTokenExists(token, tenantId)` (added 2026-08-14, expired-invite-chat-first) — a deliberately weaker sibling check: does a `members` row with this exact `token` + `tenant_id` exist at all, with no regard to `used_at`/`revoked_at`/`status`? Returns a plain `boolean`, not a row. Exists only to distinguish "a real token that's since expired/been used/been revoked" from "a garbage string in the `?invite=` URL param" for `app/heirloom/page.tsx`'s gate-bypass decision (see `System Docs/Public Site.md`'s `HeirloomPage`/`chatStore` rows) — does **not** indicate the token is currently valid; callers needing that still use `validateMemberToken`. `linkInvitedMember(clerkId, email, token?, name?)` — called on `user.created`/`user.updated` webhook: upserts the users row, finds an invited row by token (primary, now also selecting `name`) or email (fallback, case-insensitive, also selecting `name`), updates it with `clerk_id`, `user_id`, `status='active'`, `source='invite'`, `used_at=now()`, and, as of 2026-08-14 (PR #371), `name` — only when the invited row's own `name` is currently null, never overwriting an existing one; `name` is passed by the webhook handler, derived from Clerk's `firstName + lastName`, the same derivation it already uses for its own `syncMember` call below. Returns `false` (webhook falls back to `syncMember`) when no invited row matches, when the `users` upsert fails, or when the final `UPDATE` fails — the latter can happen if `syncMember` already inserted an orphan row for this `clerk_id` on an earlier webhook delivery (unique-constraint collision); logs `member.user_resolve_failed` / `member.link_update_failed` (with the Postgres error code in `metadata.pg_code`) to `audit_events` on those two failure branches respectively. `acceptInvite(token, clerkUserId, supabaseUserId)` — accepts an invite by token after Clerk sign-up: finds the invited row, deletes any orphan active row that `syncMember` created (invited row had `clerk_id=null` → no upsert conflict → new active row inserted by webhook; logs `member.orphan_reconciled` when a row was actually deleted, `member.orphan_cleanup_failed` — non-fatal — if the delete errors). As of 2026-08-13 (PR #368), the orphan query also selects `name` and rescues it onto the invited row being stamped — only when exactly one orphan was deleted, its `name` is non-null, and the invited row's own `name` is currently null, never overwriting an existing name (previously that name was silently discarded on delete — see `System Docs/Known Gaps.md`). Stamps `clerk_id`, `user_id`, `status='active'`, `source='invite'`, `used_at=now()` (and the rescued `name`, if any) on the original invited row, then fires `MEMBER_INVITE_ACCEPTED` with the real `tenant_id` — moved here from the caller (`app/api/heirloom/invites/accept/route.ts`) as of 2026-08-13 (PR #367), which previously logged it with `tenant_id: null`, making every acceptance invisible to any tenant-scoped query; the route-level duplicate call was deleted. `hardDeleteMember(userId, actorId, tenantId, reason?)` — writes `MEMBER_HARD_DELETED` audit first (with `metadata.reason` when supplied), then deletes the users row (DB cascade removes members). |

**`members.user_id` write-path failure telemetry (added 2026-08-06):** `MEMBER_USER_RESOLVE_FAILED`, `MEMBER_LINK_UPDATE_FAILED`, `MEMBER_ORPHAN_CLEANUP_FAILED`, `MEMBER_ORPHAN_RECONCILED` (`services/audit/types.ts`) — added after a data-integrity gap left some active, Clerk-linked members rows with a permanently null `user_id` (root cause: `syncMember` omitted `user_id` from its upsert). See Known Gaps.md for the full incident writeup and the Studio backfill query for any pre-fix rows still affected.

**Retired:** `services/invites/` (deleted). All callers updated to use `services/members` equivalents.

**Deliberately NOT extended for reusable-story-invite-links (2026-08-10):** the durable, multi-person per-story invite link (`story_invite_links` table, one active link per story, many independent acceptances) lives entirely in `services/crm/story-invites.ts`, not here — see `System Docs/Utilities/CRM.md`. It is a wholly separate mechanism from everything in this file: no shared table, no shared function, no shared code path with `createMemberInvite`/`validateMemberToken`/`linkInvitedMember`/`acceptInvite`, which remain exactly as documented above. The two do intersect at one point only: a brand-new person accepting a story invite link gets a `members` row inserted directly with `status='active'` and `source='story_invite'` (see the `members` table's `source` column, `System Docs/Database Schema.md`) — a sibling insert shape to what `acceptInvite` produces, written by a completely different function.
