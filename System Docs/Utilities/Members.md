# Members Service

### Members service (`services/members/`)

Member invite and lifecycle operations for the `members` table. Server-only. The `invites` table is retired — invite state now lives on `members` directly via `token` / `used_at` / `invited_name` / `status = 'invited'`. Token generation uses `crypto.randomBytes(24).toString('base64url')` (32-char URL-safe string).

| File | Exports | Purpose |
|------|---------|---------|
| `members.ts` | `createMemberInvite`, `validateMemberToken`, `linkInvitedMember`, `acceptInvite`, `hardDeleteMember` (+ `MemberInviteRow`, `MembersResult`, `HEIRLOOM_TENANT_ID`) | `createMemberInvite(tenantId, actorId, invitedName?, email?, phone?)` — inserts a members row with status='invited', generates token, writes email/phone when supplied (for contact-lock invites), stamps `invited_by = actorId` for provenance (null actor = column left unset), fires `MEMBER_INVITE_CREATED` audit. `validateMemberToken(token)` — returns the members row when the token exists and `used_at IS NULL`. `linkInvitedMember(clerkId, email, token?)` — called on `user.created`/`user.updated` webhook: upserts the users row, finds an invited row by token (primary) or email (fallback, case-insensitive), updates it with `clerk_id`, `user_id`, `status='active'`, `source='invite'`, `used_at=now()`. Returns `false` (webhook falls back to `syncMember`) when no invited row matches, when the `users` upsert fails, or when the final `UPDATE` fails — the latter can happen if `syncMember` already inserted an orphan row for this `clerk_id` on an earlier webhook delivery (unique-constraint collision); logs `member.user_resolve_failed` / `member.link_update_failed` (with the Postgres error code in `metadata.pg_code`) to `audit_events` on those two failure branches respectively. `acceptInvite(token, clerkUserId, supabaseUserId)` — accepts an invite by token after Clerk sign-up: finds the invited row, deletes any orphan active row that `syncMember` created (invited row had `clerk_id=null` → no upsert conflict → new active row inserted by webhook; logs `member.orphan_reconciled` when a row was actually deleted, `member.orphan_cleanup_failed` — non-fatal — if the delete errors), stamps `clerk_id`, `user_id`, `status='active'`, `source='invite'`, `used_at=now()` on the original invited row. `hardDeleteMember(userId, actorId, tenantId)` — writes `MEMBER_HARD_DELETED` audit first, then deletes the users row (DB cascade removes members). |

**`members.user_id` write-path failure telemetry (added 2026-08-06):** `MEMBER_USER_RESOLVE_FAILED`, `MEMBER_LINK_UPDATE_FAILED`, `MEMBER_ORPHAN_CLEANUP_FAILED`, `MEMBER_ORPHAN_RECONCILED` (`services/audit/types.ts`) — added after a data-integrity gap left some active, Clerk-linked members rows with a permanently null `user_id` (root cause: `syncMember` omitted `user_id` from its upsert). See Known Gaps.md for the full incident writeup and the Studio backfill query for any pre-fix rows still affected.
